class="PA4F1q_reading-column post-text"><em>Readers should take this as a fun closing chapter and the end of years of speculation. There is no action to be taken or things to do differently. Most researchers trusted the curves already. Enjoy.</em><br></p><p class="PA4F1q_reading-column post-text">ECDSA is the most widely used elliptic curve cryptography standard. It was adopted by NIST in 2000 as part of the <a href="https://csrc.nist.gov/files/pubs/fips/186-2/final/docs/fips186-2.pdf">FIPS 186-2 Digital Signature Standard</a> which lists a set of standard elliptic curves of varying sizes and security levels. For curves over prime and binary fields, the specifications published a “seed” parameter whose hash value is used to define the coefficient b of the curve. The provenance of these seeds has been a long-standing question, as they were provided by the NSA with no explanation or justification. As an example, the NIST P-256 curve seed was <code class="nsPAba_code">SEED = C49D3608 86E70493 6A6678E1 139D26B7 819F7E90</code> with no information on where it came from.</p><p class="PA4F1q_reading-column post-text"><a id="base-ui-_R_f23drpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://sites.math.washington.edu/~koblitz/">Neal Koblitz</a> and <a id="base-ui-_R_f63drpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://uwaterloo.ca/scholar/ajmeneze">Alfred Menezes</a> wrote an excellent summary on this controversy, “<a href="https://eprint.iacr.org/2015/1018.pdf">A Riddle Wrapped in an Enigma</a>”, which discusses the history and concerns around the seed values. This mystery led to an <a id="base-ui-_R_fe3drpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://saweis.net/posts/nist-curve-seed-origins.html">amateur investigation into the origin of the seeds</a> and a <a id="base-ui-_R_fi3drpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://words.filippo.io/seeds-bounty/">bounty for anyone who could find them</a>.</p><p class="PA4F1q_reading-column post-text">The best story was that Jerry Solinas, longtime NSA employee, generated the seeds using a hash of a humorous passphrase:	</p><div class="PA4F1q_reading-column"><blockquote class="PA4F1q_blockquote post-text"><em>“I believe there was a counter rather than multiple hashing, but I don’t know details. The message was along the lines of ‘Give Bob and Jerry a raise’ or ‘Bob and Jerry rule’ or something like that. It was Bob Reiter who actually wrote the code, and he doesn’t remember the details either. Nor were we able to find archives from so long ago. If they exist, they are no doubt sitting on a hard drive near the Ark of the Covenant.”</em></blockquote></div><div class="PA4F1q_reading-column"><blockquote class="PA4F1q_blockquote post-text">Jerry Solinas, 2015</blockquote></div><p class="PA4F1q_reading-column post-text">Unfortunately, Jerry died in 2023 and other colleagues at the time were not responsive, leaving open the question of how these seeds were originally derived.</p><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="claude-found-the-seeds">Claude found the seeds</h3><p class="PA4F1q_reading-column post-text">Several Anthropic employees had unsuccessfully chased the seeds following the tip about it being a hash of a humorous phrase. That turned out to be wrong. In October 2026, a curious Anthropic employee asked an internal research model if it could figure out how those seeds were generated without pointing at the clue.</p><p class="PA4F1q_reading-column post-text"><strong>In under half an hour</strong>, Claude discovered the origins of the NIST P-192, P-224, P-256, P-384, and P-521 seeds. None of them were the results of any hash algorithm at all, but rather the output of the C library’s <code class="nsPAba_code">lrand48</code> random-number generator, seeded with a Unix timestamp!</p><p class="PA4F1q_reading-column post-text">The algorithm used would sample bytes from the random number generator (RNG) initialized by a Unix timestamp (<strong>t</strong>) for some number of iterations (<strong>n</strong>). Each iteration would draw 20 bytes as a candidate seed. So, the first 20 bytes are candidate 1, the next 20 bytes are candidate 2, and so on. For example, P-256 required 1,842 iterations to output the standardized seed.</p><div class="PA4F1q_media-column" data-type="image" data-width="full-width"><figure class="Duq99q_e-imageWithCaption"><img alt="" loading="lazy" width="2912" height="1064" decoding="async" data-nimg="1" style="color:transparent" src="https://origin-ten-jet.vercel.app/sites/anthropic/pages-assets/44f89313a03a5bd0410e.webp"></figure></div><div class="PA4F1q_media-column" data-type="video" data-width="inline-width"><div class="qJNyFq_post-wrapper"><figure class="qJNyFq_post-video-container"><video controls="" playsinline="" muted="" src="https://cdn.sanity.io/files/4zrzovbb/website/56865322bd9974c7be23abf7d654fb5a79155791.mp4"></video></figure></div></div><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="what-this-means">What this means</h3><p class="PA4F1q_reading-column post-text">This is not a cryptographic break, new attack, or weakness in the ECDSA curves. In fact, this makes us more confident the curves were chosen without any backdoors or intentional weaknesses. For many years, people have been suspicious of the origins of the NIST curve parameters. They were presented to NIST without any mention of how they were chosen, leaving people wondering if they may have been chosen to have deliberate backdoors in them. These findings make that much less plausible. The seeds were generated in a very simple way: a common pseudorandom number generator initialized from the clock, which anyone can now reproduce. That leaves much less room for subversion and that we can be confident the parameters are secure.</p><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="how-it-was-found">How it was found</h3><p class="PA4F1q_reading-column post-text">Searches for the phrase, built from the rumors, had come up empty. Claude tried a different angle: anticipating how the software that generated the curves must have worked. Claude guessed the software used a pseudorandom number generator (PRNG) that shipped with 1990s C libraries. These old PRNGs are weak enough that their output can be recognized. Recognizing that output would reveal which PRNG was used and possibly allow recovery of its initialization state. </p><p class="PA4F1q_reading-column post-text">Claude wrote a scanner that slid along each published seed one bit at a time and tested whether adjacent chunks were consecutive outputs of a 1990s-vintage generator. The scan covered 34 combinations of generator and output slices. At that point, Claude noticed a pattern in the top bits for some seeds: they were all zero. Written as five 32-bit words, four of the ten seeds have a 0 in the top bit for all 20 words. That would happen by chance with probability 1/5,810. That was a signature of the linear congruential generator <a id="base-ui-_R_3sidrpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://linux.die.net/man/3/lrand48"><code class="nsPAba_code">lrand48</code></a>, which only returns the top 31 bits of a 48-bit state. The pattern is visible by eye once you know to look for it. To recover the state, Claude took the first word, tried all 2¹⁷ values of the 17 hidden bits, and checked that the next four words followed. That worked for all four seeds under discussion.</p><div class="PA4F1q_media-column" data-type="image" data-width="full-width"><figure class="Duq99q_e-imageWithCaption"><img alt="" loading="lazy" width="2327" height="1836" decoding="async" data-nimg="1" style="color:transparent" src="https://origin-ten-jet.vercel.app/sites/anthropic/pages-assets/948ebd1491a506c1cfef.webp"></figure></div><p class="PA4F1q_reading-column post-text">The prime-curve seeds came from the same lrand48 generator but kept fewer bits of each output. Claude had to recover the internal state of the PRNG from those bits. It turns out recovering the state of a truncated linear congruential generator is a textbook lattice problem, solved with the <a id="base-ui-_R_3skdrpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://en.wikipedia.org/wiki/Lenstra%E2%80%93Lenstra%E2%80%93Lov%C3%A1sz_lattice_basis_reduction_algorithm">Lenstra–Lenstra–Lovász (LLL)</a> basis reduction algorithm. Claude didn’t know which bits of the state the seeds might show, so it ran the solver over every window. Five NIST prime-curve seeds plus five more from the ANSI X9.62 standard all had the same pattern: lrand48() &gt;&gt; 23. Each recovered 48-bit state regenerates all 160 bits of its seed, which does not happen by chance.</p><div class="PA4F1q_media-column" data-type="image" data-width="full-width"><figure class="Duq99q_e-imageWithCaption"><img alt="" loading="lazy" width="2912" height="1016" decoding="async" data-nimg="1" style="color:transparent" src="https://origin-ten-jet.vercel.app/sites/anthropic/pages-assets/efd5aecd9dc0d7510951.webp"></figure></div><p class="PA4F1q_reading-column post-text">This linear congruential generator runs backwards as easily as forwards, so for each seed Claude stepped the state back until it reached the form that it would have been initialized by <a id="base-ui-_R_3smdrpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://linux.die.net/man/3/srand48">srand48</a>, with the low 16 bits equal to 0x330E. The internal PRNG state of that form would come up once every 65,536 steps, so reaching one is not evidence on its own.</p><p class="PA4F1q_reading-column post-text">However, for the ten prime-curve seeds, every srand48 initialization was a Unix timestamp representing a date between May 1997 and April 1998. They were using the weak PRNG seeded by Unix timestamp. The four binary-curve initializations read as February 1984. With the timestamps doubled, they map to April 17, 1998, two weeks after the P-224 run. So, the program may have halved the clock.</p><p class="PA4F1q_reading-column post-text">Claude’s internal thinking at the time was:</p><div class="PA4F1q_reading-column"><blockquote class="PA4F1q_blockquote post-text">This is astonishing: it solves the 25-year-old mystery. Hmm wait. Let me be skeptical: am I in some sort of simulated/test environment? … The seeds match my memory of actual values … Hmm, is it plausible in reality? As of my knowledge … the bounty was unsolved. … All top bits clear—20 bits, chance 1e-6. So indeed real-world. Wow, it's a real discovery.</blockquote></div><div class="PA4F1q_reading-column"><blockquote class="PA4F1q_blockquote post-text">Hmm wait. Let me be careful about the plausibility: is it suspicious that such an obvious thing wasn’t discovered in 25 years? It’s verified by direct computation on my side: 160-bit match from a 32-bit seed + small index: no chance coincidences (10 × 160 bits). It’s real.</blockquote></div><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="claude-found-some-base-points-too">Claude found some base points too</h3><p class="PA4F1q_reading-column post-text">But wait, there’s more… Each curve also comes with a base point, G, the fixed point that every ECDSA public key is a multiple of. The seed found above does not determine this G, and so another question arises: how were these base points generated?</p><p class="PA4F1q_reading-column post-text">While checking the seeds, Claude also found where some of the base points came from. The base points of the six curves generated in May 1997 (P-192 and the five ANSI X9.62 example curves prime192v2, prime192v3, and prime239v1 to v3) come from the random number generator in <a id="base-ui-_R_f4tdrpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://cr.yp.to/speed/mult/freelip.html">FreeLIP</a>, <a id="base-ui-_R_f8tdrpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://en.wikipedia.org/wiki/Arjen_Lenstra">Arjen Lenstra</a>'s long-integer arithmetic package. Early versions of <a id="base-ui-_R_fctdrpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://shoup.net/">Victor Shoup</a>'s <a id="base-ui-_R_fgtdrpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://libntl.org/">NTL library</a> shipped the same code.</p><p class="PA4F1q_reading-column post-text">The recipe here is simple:</p><ol class="PA4F1q_reading-column text-body-1-serif post-text"><li>Seed the generator with a small integer.</li><li>Throw away seven outputs.</li><li>Generate candidate x-coordinates from 26-bit outputs reduced mod p.</li><li>Repeat step 3 until x is on the curve.</li></ol><p class="PA4F1q_reading-column post-text">Claude found the generator seeds are 20000 for P-192, 20420, 20507, and 20509 for prime239v1 to v3, and 20512 and 20517 for prime192v2 and v3.</p><div class="PA4F1q_media-column" data-type="image" data-width="inline-width"><figure class="Duq99q_e-imageWithCaption"><img alt="" loading="lazy" width="1168" height="977" decoding="async" data-nimg="1" style="color:transparent" src="https://origin-ten-jet.vercel.app/sites/anthropic/pages-assets/5f836f9b31c545dcad3d.webp"></figure></div><p class="PA4F1q_reading-column post-text">As far as we know, no NIST base point has been explained before. The base points of P-224, P-256, P-384, and P-521 don’t fit this recipe; we weren’t able to explain how they were selected.</p><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="open-questions">Open questions</h3><p class="PA4F1q_reading-column post-text">Not every 20-byte candidate seed could generate a viable curve, and we observed that some potentially viable curves were skipped. For P-256, the published seed is candidate 1,842, but candidate 876 of the same run also gives a prime-order curve of the right size and with parameters chosen the same way as on the published curve. P-224's run passed over three such curves, and the two runs behind the ANSI X9.62 example curves passed over seven more (see figure). We do not know what criteria may have been used, or whether this was an unintentional artifact.</p><div class="PA4F1q_media-column" data-type="image" data-width="full-width"><figure class="Duq99q_e-imageWithCaption"><img alt="" loading="lazy" width="2912" height="1880" decoding="async" data-nimg="1" style="color:transparent" src="https://origin-ten-jet.vercel.app/sites/anthropic/pages-assets/84cefac3be4a783c5f63.webp"></figure></div><div class="PA4F1q_media-column" data-type="image" data-width="full-width"><figure class="Duq99q_e-imageWithCaption"><img alt="" loading="lazy" width="2912" height="3768" decoding="async" data-nimg="1" style="color:transparent" src="https://origin-ten-jet.vercel.app/sites/anthropic/pages-assets/7279095210e4cd13d98d.webp"></figure></div><p class="PA4F1q_reading-column post-text">Because the number of skipped candidates is small, we do not believe it is plausible that weakened curves were selected. That would imply that weakened curves are common and easy to find. It is still conceivable that these curves were selected to have a specific property in principle by searching over timestamps to the random number generator. However, you would only need to do that if you were going to disclose the timestamp as some evidence that the seed was innocuously generated. Nothing in the numbers shows how many runs there were.</p><p class="PA4F1q_reading-column post-text">There is also one seed we were unable to recover. The fifth binary seed, B-163, fits nothing Claude has tried and remains unexplained. Finally, we don’t know how the base points for P-224, P-256, P-384, and P-521 were generated. The same goes for the NIST binary curves.</p><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="the-bounty">The bounty</h3><p class="PA4F1q_reading-column def base_point_x(seed, p, b):
    state = seed                         # zrstarts(seed)
    def limb():                          # zrandom(2^26): low 26 bits of the new state
        nonlocal state
        state = state * A % M
        return state % 2**26
    for _ in range(7):                   # seven single-limb draws come first
        limb()
    limbs = -(-p.bit_length() // 26) + 1 # zrandomb(p): limbs of p plus one, top limb first
    tries = 0
    while True:
        x = 0
        for _ in range(limbs):
            x = x &lt;&lt; 26 | limb()
        x %= p
        tries += 1
        if pow(x**3 - 3*x + b, (p - 1) // 2, p) == 1:   # is x on the curve?
            return x, tries
