data-theme="ivory"><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="key-findings">Key findings</h3><ul class="PA4F1q_reading-column text-body-1-serif post-text"><li>Building on <a target="_blank" href="/research/measuring-agent-autonomy" rel="noopener noreferrer">prior</a> <a target="_blank" href="/research/how-ai-is-transforming-work-at-anthropic" rel="noopener noreferrer">work</a>, we introduce a framework for studying interactive agentic coding based on a <a target="_blank" href="/research/clio" rel="noopener noreferrer">privacy-preserving analysis</a> of ~400,000 Claude Code sessions from between October 2025 and April 2026. We evaluate the composition of tasks, human-AI collaboration, and success rates.</li><li>In a typical session, people make most of the planning decisions (what to do) and Claude makes most of the execution decisions (how to do it). The greater domain expertise a person brings to a session, the more work Claude does per instruction. On coding tasks, every major occupation succeeds––accomplishes what the person set out to do, with verifiable evidence like passing tests or committed work––at nearly the same rate as software engineers, on average.</li><li>The more domain expertise a person has, the more often the session ends in success—though the gap between intermediate and expert users is modest. Over the seven months we observe, the share of sessions spent debugging fell by nearly half, and usage shifted toward more end-to-end agentic use: deploying and running code, analyzing data, and writing non-code documents.</li><li>Over those seven months, the value of the typical task, which we estimate through a comparison to freelance job postings, rose in almost every kind of work—about 25% on average.</li></ul><h2 class="tOQyXa_headline-4 PA4F1q_reading-column post-heading" data-component="Headline" id="introduction">Introduction</h2><p class="PA4F1q_reading-column post-text">Agentic coding has taken off. The share of GitHub projects with coding agent activity has more than doubled since late 2025,<sup class="caption PA4F1q_sup PA4F1q_footnote-marker"><a href="#footnote-1" id="footnote-ref-1" class="PA4F1q_footnote-ref" role="doc-noteref" aria-label="Footnote 1">1</a></sup> and Claude Code users now spend an average of 20 hours per week using the tool.<sup class="caption PA4F1q_sup PA4F1q_footnote-marker"><a href="#footnote-2" id="footnote-ref-2" class="PA4F1q_footnote-ref" role="doc-noteref" aria-label="Footnote 2">2</a></sup> Can people without formal coding experience successfully direct an agent through complex technical work? And what will rapid adoption and improvement of these tools mean for knowledge work broadly? While we don’t have full answers to these questions yet, we look to Claude Code usage data for early signals.</p><p class="PA4F1q_reading-column post-text">This report provides evidence on how Claude Code is used in practice, based on a <a target="_blank" href="/research/clio" rel="noopener noreferrer">privacy-preserving analysis</a> of ~400,000 interactive sessions from ~235,000 people between October 2025 and April 2026. It builds on prior work focused on <a target="_blank" href="/research/measuring-agent-autonomy" rel="noopener noreferrer">measures of autonomy</a> in Claude Code sessions, and <a target="_blank" href="/research/how-ai-is-transforming-work-at-anthropic" rel="noopener noreferrer">how Claude Code is changing work at Anthropic</a>.<sup class="caption PA4F1q_sup PA4F1q_footnote-marker"><a href="#footnote-3" id="footnote-ref-3" class="PA4F1q_footnote-ref" role="doc-noteref" aria-label="Footnote 3">3</a></sup> Here, we introduce a framework for describing interactive AI coding-assistant usage: what kind of work is being done, who is doing it, and whether it succeeds. We focus on Claude Code usage through a command-line interface (CLI), <a id="base-ui-_R_fk5drpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" target="_blank" href="http://claude.ai" rel="noopener noreferrer">Claude.ai</a>, or the Claude Code desktop app.<sup class="caption PA4F1q_sup PA4F1q_footnote-marker"><a href="#footnote-4" id="footnote-ref-4" class="PA4F1q_footnote-ref" role="doc-noteref" aria-label="Footnote 4">4</a></sup> By tracking how agentic coding usage changes as models get more capable, we can better understand how these tools affect the labor market for coding professionals and knowledge workers.</p><p class="PA4F1q_reading-column post-text">What happens on Claude Code may be a preview of where knowledge work is headed, as agents become embedded in non-coding work. We find that Claude is handling more complex and more valuable tasks. At the same time, there remains a clear division of labor in agentic coding: People decide what to build, and the agent decides how to build it.</p><p class="PA4F1q_reading-column post-text">We also see evidence that domain expertise, and not coding proficiency, amplifies effective use of the tool. In particular, domain experts succeed more often, and more easily recover from errors and misunderstandings. However, the gap between experts and intermediates is modest—suggesting that proficiency in a domain is enough to use the tool almost as effectively as those with deep mastery.</p><p class="PA4F1q_reading-column post-text">These findings give us an early read on possible transitions in the labor market. In our data, success is determined by how well a person understands the problem they are trying to solve, not whether they’re trained in coding. If these patterns hold across the economy, it suggests that while agentic coding tools may be absorbing some implementation-heavy work, they are also rewarding those with firm understanding of the problems they solve on the job. Coding agents are not substituting for domain expertise—the more understanding a worker brings to an agent, the more quality work the agent is able to do.</p><h2 class="tOQyXa_headline-4 PA4F1q_reading-column post-heading" data-component="Headline" id="the-division-of-labor">The division of labor</h2><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="what-people-use-claude-code-for">What people use Claude Code for</h3><p class="PA4F1q_reading-column post-text">To understand what people are using Claude Code for, we classify each session into one of nine work modes—the single activity that best describes what the session is trying to accomplish.<sup class="caption PA4F1q_sup PA4F1q_footnote-marker"><a href="#footnote-5" id="footnote-ref-5" class="PA4F1q_footnote-ref" role="doc-noteref" aria-label="Footnote 5">5</a></sup> Four modes involve writing or maintaining code directly: <em>building</em> something new, <em>fixing</em> something broken, <em>testing</em> code, and <em>orchestrating</em> other agents or automated pipelines. Another category is <em>operating</em> software—deploying, configuring, running pipelines, monitoring systems. Two categories are more about working out what to do: <em>understanding</em> how an existing system works, and <em>planning</em> a change before making it. And two take actions unrelated to code, or where code is incidental to the final product: <em>analyzing</em> data, and <em>communicating</em> via presentations and other prose-based documents.</p><p class="PA4F1q_reading-column post-text">About 56% of sessions consist of writing (25%), fixing (26%), or testing and orchestrating code (5%). Operating software comprises 17%, while 14% of sessions are planning or exploring, and 13% produce analysis or prose (Figure 1).</p><div class="PA4F1q_media-column" data-type="image" data-width="inline-width"><figure class="Duq99q_e-imageWithCaption"><img alt="" loading="lazy" width="1920" height="1080" decoding="async" data-nimg="1" style="color:transparent" src="https://origin-ten-jet.vercel.app/sites/anthropic/pages-assets/c056981345c5b9af10ca.webp"><figcaption style="--figure-label:&quot;Figure 1&quot;" class="RMuY0W_root -LJkNq_container -LJkNq_container--default" data-component="RichTextWrapper"><div class="tOQyXa_caption-1 -LJkNq_text" data-component="Caption"><strong>The nine modes of work: </strong>Each interactive session is classified into the single mode that best describes what it is trying to accomplish.<br></div></figcaption></figure></div><p class="PA4F1q_reading-column post-text">We classify each session by having a model read its transcript, then using our privacy-preserving analysis tool, we check them against telemetry that's recorded automatically for every session, including whether any lines of code were added or deleted. The two sources have high agreement—for instance, more than 90% of sessions our classifier labeled as creating or modifying code showed code changes in the telemetry. See the <a target="_blank" href="https://www-cdn.anthropic.com/files/4zrzovbb/website/a94728142a45694292336165947f8d6e3e1a357e.pdf" rel="noopener noreferrer">Appendix<strong> </strong></a>for details.</p><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="who-decides-what">Who decides what</h3><p class="PA4F1q_reading-column post-text">How autonomous is Claude Code? Capability evaluations suggest the ceiling is high and rising: on benchmarks such as <a id="base-ui-_R_3sgdrpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" target="_blank" href="https://metr.org/time-horizons/" rel="noopener noreferrer">METR's time-horizon evaluations</a>, frontier models can now complete software tasks that would take a person hours, autonomously working through obstacles along the way. But what does usage actually look like in practice? Here, we look at how much steering is done by the person and by Claude in real sessions.</p><p class="PA4F1q_reading-column post-text">We investigate this question from two angles. First, we focus on the extent to which people are entrusting <em>decisions</em> to Claude, and second we look at how many <em>actions </em>they give to Claude. To understand the division of decision-making in a session, we build a privacy-preserving decision attribution classifier based on the content of a session. We ask a classifier to list all the meaningful decisions in a session. We separate these decisions into planning (what to do, which approach to take, what counts as done) and execution (which files to change, what code to write, what language to write in, which commands to run). The classifier then attributes each decision to Claude or to the user, giving every session two numbers: the user's share of planning decisions and the user's share of execution decisions.</p><p class="PA4F1q_reading-column post-text">On average, people make about 70% of the planning decisions but only 20% of the execution decisions (Figure 2). In practice, there is a clear division of labor in agentic coding––people decide what to build, and the agent decides how to build it.</p><p class="PA4F1q_reading-column post-text">To understand the delegation of actions in a session, we look at the session’s structure instead of its content. A Claude Code session involves Claude and the user going back and forth trading prompts (from the user) and actions (taken by Claude)––the user writes a prompt and Claude goes off and does some work, and then the user writes another prompt, and so forth. In a typical session, there are about four such turns. In our historical data from October to April, each prompt the user sends sets off a chain of around 10 actions taken by Claude on average––and sometimes over 100.<sup class="caption PA4F1q_sup PA4F1q_footnote-marker"><a href="#footnote-6" id="footnote-ref-6" class="PA4F1q_footnote-ref" role="doc-noteref" aria-label="Footnote 6">6</a></sup> In each turn, Claude reads files, edits code, runs commands, and writes on average 2,400 words of output.</p><p class="PA4F1q_reading-column post-text">How much Claude does between check-ins largely tracks who is making the decisions. When the user keeps control of execution (i.e. makes over 80% of execution decisions), Claude takes fewer actions per turn (about eight actions). And when Claude takes control of planning (i.e. makes over 80% of planning decisions), it takes on the highest number of actions (about 16).</p><div class="PA4F1q_media-column" data-type="image" data-width="inline-width"><figure class="Duq99q_e-imageWithCaption"><img alt="" loading="lazy" width="1920" height="1080" decoding="async" data-nimg="1" style="color:transparent" src="https://origin-ten-jet.vercel.app/sites/anthropic/pages-assets/07d8f30c8451ccad8bce.webp"><figcaption style="--figure-label:&quot;Figure 2&quot;" class="RMuY0W_root -LJkNq_container -LJkNq_container--default" data-component="RichTextWrapper"><div class="tOQyXa_caption-1 -LJkNq_text" data-component="Caption"><strong>Claude's share of planning and execution decisions: </strong>Distribution across sessions of the share of planning decisions (what to do) and execution decisions (how to do it) attributed to Claude rather than the user. In the typical session, the user makes about 70% of planning decisions while Claude makes about 80% of execution decisions.<br><br></div></figcaption></figure></div><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="level-of-expertise">Level of expertise</h3><p class="PA4F1q_reading-column post-text">From each transcript, Claude rates the user's apparent expertise at the task on a five-point scale from novice to expert. The expertise classifier looks for three signals: how precisely the user frames their directions, what they ask Claude to verify, and whether the user tends to correct Claude or Claude tends to correct the user. Note that expertise is capturing something quite different from job title or general ability, and, crucially, it is <em>task-specific</em>. A senior engineer asking their first Rust question is a beginner at Rust. An accountant who has never used Python, but tells Claude exactly which reconciliation rules a Python script must enforce and catches the edge case it mishandles at month-end close, is an expert at that task.</p><p class="PA4F1q_reading-column post-text">The table below shows how we defined each expertise level in the classifier along with an example request from a public dataset of coding agent sessions, <a id="base-ui-_R_3sodrpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" target="_blank" href="https://huggingface.co/datasets/SALT-NLP/SWE-chat" rel="noopener noreferrer">SWE-chat</a>. The conversation categorized as Novice gives generic instructions with no implied domain-specific knowledge. The Expert conversation conveys deep knowledge of the codebase and technical environment.</p><div class="PA4F1q_media-column" data-type="image" data-width="inline-width"><figure class="Duq99q_e-imageWithCaption"><img alt="" loading="lazy" width="1850" height="1830" decoding="async" data-nimg="1" style="color:transparent" src="https://origin-ten-jet.vercel.app/sites/anthropic/pages-assets/678557333d0a57d2891a.webp"><figcaption style="--figure-label:&quot;Table 1&quot;" class="RMuY0W_root -LJkNq_container -LJkNq_container--default" data-component="RichTextWrapper"><div class="tOQyXa_caption-1 -LJkNq_text" data-component="Caption"><strong>Expertise classifier: </strong>The examples paraphrase, anonymize and condense real sessions labeled by our classifiers. Many of the sessions used in the table come from a public dataset of agentic coding sessions, <a href="https://huggingface.co/datasets/SALT-NLP/SWE-chat">SWE-chat</a>.<br></div></figcaption></figure></div><p class="PA4F1q_reading-column post-text">We quantify how expertise relates to Claude’s output and activity per prompt. In typical novice sessions, each prompt sets off about five Claude actions and roughly 600 words of output, while expert sessions set off action chains more than twice as long (12 actions) carrying five times the output (3,200 words) (Figure 3). This gap between novice and expert sessions appears within every kind of work and every band of task value.</p><p class="PA4F1q_reading-column post-text">These measures complement the autonomy measures in our <a target="_blank" href="/research/measuring-agent-autonomy" rel="noopener noreferrer">prior report on Claude Code</a>, which tracked how long the agent runs and how often people approve its actions automatically. Our decision attribution measure, by contrast, captures who makes the substantive decisions in a session as a whole, while our measures of output and actions per prompt measure how much autonomous activity from Claude each human prompt sets off.</p><div class="PA4F1q_media-column" data-type="image" data-width="inline-width"><figure class="Duq99q_e-imageWithCaption"><img alt="" loading="lazy" width="1920" height="1080" decoding="async" data-nimg="1" style="color:transparent" src="https://origin-ten-jet.vercel.app/sites/anthropic/pages-assets/02932fd0e6b85e3042f9.webp"><figcaption style="--figure-label:&quot;Figure 3&quot;" class="RMuY0W_root -LJkNq_container -LJkNq_container--default" data-component="RichTextWrapper"><div class="tOQyXa_caption-1 -LJkNq_text" data-component="Caption"><strong>Claude does more per prompt for more expert users: </strong>Claude produces more actions (left bar) and text output per prompt (right bar) for more expert users. Boxes span the interquartile range (split at the median). Whiskers represent the 5th to 95th percentile. White dots are geometric means. Both upward trends are statistically significant (p &lt; 0.001), as is each adjacent-level step, and they remain significant (at +9% actions and +13% output per expertise level) in a regression controlling for work mode, task value, month, occupation, and model family, with standard errors clustered by user.<br></div></figcaption></figure></div><h2 class="tOQyXa_headline-4 PA4F1q_reading-column post-heading" data-component="Headline" id="who-uses-claude-code-and-for-what">Who uses Claude Code, and for what</h2><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="the-users">The users</h3><p class="PA4F1q_reading-column post-text">To understand who is doing this work, we infer each user's occupation from the session transcript, mapping it to one of 23 major groups in the Bureau of Labor Statistics’ Standard Occupational Classification (SOC) taxonomy. The classifier is instructed to rely only on signals such as the project context the agent loads at the start of a session, the names and structure of their files, any artifacts they reference (e.g., legal filings, clinical data, financial reports, a curriculum, etc.) and vocabulary they use.<sup class="caption PA4F1q_sup PA4F1q_footnote-marker"><a href="#footnote-7" id="footnote-ref-7" class="PA4F1q_footnote-ref" role="doc-noteref" aria-label="Footnote 7">7</a></sup> It is explicitly instructed <em>not</em> to treat the act of coding as evidence of a coding profession. A session is classified into the coding SOC code (Computer and Mathematical Occupations) only when there is clear signal that software or data work is the user’s job. A session in which a lawyer builds a script to automatically flag missing clauses across a folder of contracts is mapped into Legal Occupations, even if the session’s work is primarily software. The session is left unclassified when there is no signal about the user’s occupation.</p><p class="PA4F1q_reading-column post-text">We were able to infer occupation in about 70% of sessions. Within this set, Computer and Mathematical Occupations, a category which encompasses most software-related jobs, is unsurprisingly the largest group. The next largest are Business and Financial Operations; Arts, Design, and Media; Management; and Life, Physical, and Social Sciences. The fastest-growing non-software occupation groups in our sample are management, sales, and legal occupations.</p><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="the-work">The work</h3><p class="PA4F1q_reading-column post-text">The composition of the work done with Claude Code changed substantially between October 2025 and April 2026. The clearest change is that the share of sessions spent fixing broken code fell from 33% to 19% (Figure 4). In its place, we saw a greater share of the work that surrounds code. Operating software grew from 14% to 21% of sessions. Writing and data analysis roughly doubled, from about 10% to 20% of sessions.</p><p class="PA4F1q_reading-column post-text">The tasks themselves also grew more valuable. We approximate each session's economic value by asking what the work would cost on a freelance marketplace, calibrated against a public dataset of real postings. By this measure, the estimated value of the average session rose by 27% between October and April. The rise holds across many kinds of work. Building, operating, and fixing-type tasks all grew more valuable by roughly a third or more (about 43%, 34%, and 32% respectively). These price estimates are coarse, so we use them primarily to compare tasks to one another over time, not as dollar values to be read literally.<sup class="caption PA4F1q_sup PA4F1q_footnote-marker"><a href="#footnote-8" id="footnote-ref-8" class="PA4F1q_footnote-ref" role="doc-noteref" aria-label="Footnote 8">8</a></sup> For details about the construction of the task estimator, see the <a target="_blank" href="https://www-cdn.anthropic.com/files/4zrzovbb/website/a94728142a45694292336165947f8d6e3e1a357e.pdf" rel="noopener noreferrer">Appendix</a><strong>.</strong></p><div class="PA4F1q_media-column" data-type="image" data-width="inline-width"><figure class="Duq99q_e-imageWithCaption"><img alt="" loading="lazy" width="1920" height="1080" decoding="async" data-nimg="1" style="color:transparent" src="https://origin-ten-jet.vercel.app/sites/anthropic/pages-assets/567d607b2d27f16c86aa.webp"><figcaption style="--figure-label:&quot;Figure 4&quot;" class="RMuY0W_root -LJkNq_container -LJkNq_container--default" data-component="RichTextWrapper"><div class="tOQyXa_caption-1 -LJkNq_text" data-component="Caption"><strong>The composition and value of Claude Code work, October 2025 to April 2026: </strong>Share of sessions in each work mode over the seven-month window. The share of sessions fixing broken code fell from 33% to 19%, while operating software, analyzing data, and writing documents grew.<br><br></div></figcaption></figure></div><h2 class="tOQyXa_headline-4 PA4F1q_reading-column post-heading" data-component="Headline" id="success-depends-on-what-the-user-brings">Success depends on what the user brings</h2><p class="PA4F1q_reading-column post-text">The estimated value of a task is one way to get a sense of how Claude Code is helping people do their work. Another angle is to look at how many sessions are successful, and what characteristics of a session are linked to success. Across all our measures of success, we see a clear pattern: the more expertise a person exhibits in a session, the higher the likelihood of success. Most of the gain is concentrated at the lower end of the expertise scale––the gap between novice sessions and intermediate sessions is bigger than the gap between intermediate and expert.</p><p class="PA4F1q_reading-column post-text">Before turning to the characteristics of successful sessions, we should be precise about how we measure success. We do not observe users’ real-world outcomes, and we cannot ask them directly whether they got what they wanted out of Claude. Instead, we rely on two complementary transcript-based measures. The first, <em>judged success</em><strong>, </strong>comes<strong> </strong>from a classifier that reads the full transcript and decides whether the person succeeded in doing what they set out to do (with options: succeeded, partially succeeded, failed, no clear goal). Two companion classifiers then rate the strength of the evidence for that judgment to determine <em>verified success</em>. A success signal classifier<strong> </strong>looks for verifiable evidence of success. In particular, it looks for git activity like commits and pull requests matching the work, as well as test suites passing, and explicit affirmation from the user. It scores the session from "no signal" to “weak signal” (1) to "multiple hard signals” (5). A parallel failure signal scores the evidence that things went wrong—errors, failed tests, retries, the user pushing back on the output. Verified success requires <em>both</em> that the session is judged successful and there is at least one hard verifiable signal of success. For the following analysis, which is focused on the degree of success or failure in a session, we exclude sessions classified as having “no clear goal,” which comprise about 7.7% of our full sample.</p><h2 class="tOQyXa_headline-4 PA4F1q_reading-column post-heading" data-component="Headline" id="the-returns-to-expertise">The returns to expertise</h2><p class="PA4F1q_reading-column post-text">So what kinds of sessions are most successful? It turns out that the expertise rating of a session, described above, matters a great deal for the success of a session.</p><p class="PA4F1q_reading-column post-text">One might worry that expertise isn't the real driver—perhaps experts simply pick different tasks, or differ in other ways. Throughout this section, we partially address this worry by comparing sessions doing the same kind of work, at the same estimated value, in the same month, on the same subject, from people in the same broad occupation group, and ask how outcomes differ by the person’s rated expertise.</p><div class="PA4F1q_media-column" data-type="image" data-width="inline-width"><figure class="Duq99q_e-imageWithCaption"><img alt="" loading="lazy" width="1850" height="1487" decoding="async" data-nimg="1" style="color:transparent" src="https://origin-ten-jet.vercel.app/sites/anthropic/pages-assets/5e569961a2a6ad6b8ac4.webp"><figcaption style="--figure-label:&quot;Table 2&quot;" class="RMuY0W_root -LJkNq_container -LJkNq_container--default" data-component="RichTextWrapper"><div class="tOQyXa_caption-1 -LJkNq_text" data-component="Caption"><strong>Definitions of success and failure derived from classifiers: </strong>The examples paraphrase and summarize real sessions from a public dataset of agentic coding interactions, <a href="https://huggingface.co/datasets/SALT-NLP/SWE-chat">SWE-chat</a>, labeled by our classifiers.</div></figcaption></figure></div><p class="PA4F1q_reading-column post-text">Across all of our success measures, the more expertise a person exhibits in a session, the more likely it is that the session succeeds. A novice-rated session reaches our strictest measure, <em>verified success,</em> 15% of the time and at least partial success 77% of the time. A session rated intermediate or up reaches verified success 28-33% of the time and partial success 91-92% of the time (Figure 5).</p><p class="PA4F1q_reading-column post-text">In each measure, most of the gain comes from moving from novice to intermediate; between intermediate and expert, the slope decreases. In the <a target="_blank" href="https://www-cdn.anthropic.com/files/4zrzovbb/website/a94728142a45694292336165947f8d6e3e1a357e.pdf" rel="noopener noreferrer">Appendix</a>, we give details about the regressions behind Figure 5.</p><div class="PA4F1q_media-column" data-type="image" data-width="inline-width"><figure class="Duq99q_e-imageWithCaption"><img alt="" loading="lazy" width="1920" height="1080" decoding="async" data-nimg="1" style="color:transparent" src="https://origin-ten-jet.vercel.app/sites/anthropic/pages-assets/f0807671015ecdf329e7.webp"><figcaption style="--figure-label:&quot;Figure 5&quot;" class="RMuY0W_root -LJkNq_container -LJkNq_container--default" data-component="RichTextWrapper"><div class="tOQyXa_caption-1 -LJkNq_text" data-component="Caption"><strong>Expertise and how sessions end: </strong>Session outcomes by the user's rated expertise at the task, on a five-point scale from novice to expert. The left panel includes all sessions. The middle and right panels restrict to sessions that hit trouble (failure signals &gt; 3) and show the share that still end in various definitions of success and failure. Each point is an adjusted rate––we estimate the differences between expertise levels by comparing only sessions that share the same work mode, the same task-value band, the same month, the same task subject, and the same kind of user (software-related occupation or not). Details about the regressions behind these points are in the Appendix. Whiskers are confidence intervals on sample means (most are too small to be visible in this plot). These plots exclude sessions judged by the success outcome classifier to have no clear goal.<br><br></div></figcaption></figure></div><p class="PA4F1q_reading-column post-text">A similar gradient appears in sessions that run into challenges along the way. We say a session <em>hits trouble</em> when the failure signal records verified evidence of failure. This could be an error, a failed test, multiple attempts to do the same thing, or the user expressing frustration or dissatisfaction. Among sessions that hit trouble, the share that are verified successes rises from 4% for novice-rated sessions to 15% for expert-rated ones, accounting for all the controls described above (Figure 5). Looking at the looser measures, we find that the share of at least partial success is 60% for novice and 80-81% for intermediate through expert sessions.</p><p class="PA4F1q_reading-column post-text">We also track the inverse relationship––expertise versus various measures of failure. Note that in this analysis, the sessions judged as failures are those that do not even partially succeed. We say a troubled session is <em>abandoned </em>if it is judged as failed <em>and</em> zero lines of code are written: 19% of sessions where the user appears to be a novice end abandoned, against 5-7% for everyone else. In other words, the least experienced users are more likely to give up when they are struggling to get the outcome they are after. Part of the value of expertise appears to be the ability to steer the agent in the right direction.<sup class="caption PA4F1q_sup PA4F1q_footnote-marker"><a href="#footnote-9" id="footnote-ref-9" class="PA4F1q_footnote-ref" role="doc-noteref" aria-label="Footnote 9">9</a></sup></p><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="occupation-may-matter-less-than-expertise">Occupation may matter less than expertise</h3><p class="PA4F1q_reading-column post-text">People in software-related occupations reach verified success in about 30% of their sessions overall, while users from other professions reach verified success about 26% of the time. Among sessions that produce code (i.e., sessions that add or modify at least one line of code), those numbers are 34% and 29% respectively (Figure 6). The gap between software-related occupations and other occupations narrows under our looser definition of success––with both groups reaching at least partial success in code-producing sessions 89% and 88% of the time, respectively. That five-point gap is small, and it has neither widened nor narrowed over seven months, even as the success rates in both groups increased. In code-producing sessions, every one of the ten largest occupations in our dataset lands within seven points of software engineers in terms of their success. Management occupations are highest on verified success, slightly above the software engineering occupations. Their higher verified success rates may reflect management skills that transfer to directing an agent. But they may also partly reflect our measurement: verification rests partially on explicit confirmation in the transcript, and managers may be more likely to communicate when they get what they ask for.<sup class="caption PA4F1q_sup PA4F1q_footnote-marker"><a href="#footnote-10" id="footnote-ref-10" class="PA4F1q_footnote-ref" role="doc-noteref" aria-label="Footnote 10">10</a></sup></p><div class="PA4F1q_media-column" data-type="image" data-width="full-width"><figure class="Duq99q_e-imageWithCaption"><img alt="" loading="lazy" width="1920" height="1080" decoding="async" data-nimg="1" style="color:transparent" src="https://origin-ten-jet.vercel.app/sites/anthropic/pages-assets/6f74fc60f4972c8ea30c.webp"><figcaption style="--figure-label:&quot;Figure 6&quot;" class="RMuY0W_root -LJkNq_container -LJkNq_container--default" data-component="RichTextWrapper"><div class="tOQyXa_caption-1 -LJkNq_text" data-component="Caption"><strong>Verified and judged success rates in coding sessions by inferred occupation: </strong>Share of sessions meeting strict definitions of success––judged success and verified success––among sessions that add or change at least one line of code, by the user's inferred occupational group, for the ten largest groups. Every group is within seven percentage points of software/math users (SOC Code Computer and Mathematical Occupations). Error bars are 95% confidence intervals computed on distinct accounts.<br><br></div></figcaption></figure></div><h2 class="tOQyXa_headline-4 PA4F1q_reading-column post-heading" data-component="Headline" id="looking-ahead">Looking ahead</h2><p class="PA4F1q_reading-column post-text">The results in this report offer an emerging picture of how agentic coding amplifies some forms of knowledge and skills, while substituting for others. In sessions that produce code, every major occupation succeeds at rates within a few points of those in software-related occupations. It appears that coding agents are making a coding background less relevant to successful programming.</p><p class="PA4F1q_reading-column post-text">At the same time, successful sessions are more likely to exhibit domain expertise. Sessions rated expert reach verified success more than twice as often as those rated novice, and when a session hits trouble, novices abandon the session at several times the rate of everyone else. The shape of the collaboration gives this picture more color—domain experts are able to direct Claude to do more work with each instruction they give. So, the ability to steer Claude toward success comes more from command of a domain than from the ability to write code. A person with such command, in any field, may now be able to do technical work they previously could not. A person without any such expertise will get far less from the same tool. And the gains come mostly from competence, not mastery––a working grasp of the domain captures most of the benefit, while deep specialization adds only a bit more beyond that.</p><p class="PA4F1q_reading-column post-text">These findings are preliminary. As in most of our research, we cannot measure real-world outcomes, like whether code written in a session is actually used or discarded thereafter, or whether it produces an economically valuable artifact. In addition, the non-interactive usage this report excludes is a substantial share of activity. Developing a framework to measure it is a priority for future work. And all of our classifications of sessions depend on a model's reading of the transcript. In the <a target="_blank" href="https://www-cdn.anthropic.com/files/4zrzovbb/website/a94728142a45694292336165947f8d6e3e1a357e.pdf" rel="noopener noreferrer">Appendix</a>, we show that our classifiers track independent telemetry in expected directions, and agree with a strong reference model on the majority of sessions. But classifiers remain challenging to validate at scale, and Claude Code sessions add further difficulty, as they may be too long and complex for human labels to serve as ground truth.</p><p class="PA4F1q_reading-column post-text">The picture in this report will be updated as the models, the users, and the division of labor between them change. We hope that these measures will allow us to track consequential shifts as they happen. For instance, if the returns to expertise begin to decrease over time, that would suggest that models are starting to supply the essential judgment that users currently bring, and that the gains from these tools are broadening beyond domain experts. If the share of coding sessions completed successfully by users outside software occupations continues to grow, it could indicate that software production is becoming a part of ordinary work in every field, rather than the product of a single occupation. These shifts would change who benefits from agentic coding, and by how much, and would have implications for what is most valued in the labor market.</p><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="appendix">Appendix</h3><p class="PA4F1q_reading-column post-text">Available <a target="_blank" href="https://www-cdn.anthropic.com/files/4zrzovbb/website/a94728142a45694292336165947f8d6e3e1a357e.pdf" rel="noopener noreferrer">here</a><a target="_blank" href="https://www-cdn.anthropic.com/files/4zrzovbb/website/7426c33b0e75ab4771c465d30d5bc1019bdd0c9c.pdf" rel="noopener noreferrer">.</a><br></p></div><div class="EaEYjq_Footnotes" style="visibility: visible; translate: none; rotate: none; scale: none; transform: translate3d(0px, 0px, 0px); opacity: 0.8665;"><h2 class="tOQyXa_headline-4" data-component="Headline">Footnotes</h2><div class="EaEYjq_FootnotesList" data-multi="true"><p id="footnote-1" class="EaEYjq_FootnoteItem"><span class="text-caption-1 EaEYjq_Sup"> <!-- -->01</span><a href="https://arxiv.org/abs/2601.18341">A first study</a>, covering 128,000 public repositories, detected coding-agent activity in an estimated 16-23% of projects as of the end of October 2025. <a href="https://arxiv.org/abs/2606.07448">A follow-up study</a> using the same methodology found adoption rates more than twice as high among projects created after that period.
