PA4F1q_sup">3</sup>, Zac Hatfield-Dodds<sup class="caption PA4F1q_sup">2</sup>, Nicholas Carlini<sup class="caption PA4F1q_sup">2</sup><br><sup class="caption PA4F1q_sup">1</sup>MATS, <sup class="caption PA4F1q_sup">2</sup>Anthropic, <sup class="caption PA4F1q_sup">3</sup>Northeastern University</em></p><p class="PA4F1q_reading-column post-text"><strong><em>We developed an agent that can efficiently identify bugs in large software projects. To do this, our agent infers general properties of code that should be true, and then by applying property-based testing—a technique similar to fuzz testing—we are able to discover bugs in top Python packages like NumPy, SciPy, and Pandas. After extensive manual validation, we are in the process of reporting these bugs to the developers, several of which have already been patched.</em></strong></p><p class="PA4F1q_reading-column post-text">For more information, read the full <a id="base-ui-_R_7k3drpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://arxiv.org/abs/2510.09907">paper</a>, take a look at the <a id="base-ui-_R_7o3drpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://github.com/mmaaz-git/agentic-pbt">GitHub repository</a>, or browse the bugs we found at our <a id="base-ui-_R_7s3drpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://mmaaz-git.github.io/agentic-pbt-site/">site</a>.</p><h2 class="tOQyXa_headline-4 PA4F1q_reading-column post-heading" data-component="Headline" id="introduction">Introduction</h2><p class="PA4F1q_reading-column post-text">Ensuring that programs are bug-free is one of the most challenging aspects of software engineering. Bugs frequently continue to lurk despite the developer’s best effort. The most common approach to testing code is with <em>example-based&nbsp;tests</em>: the developer writes out a specific example use-case, and then verifies that the actual output matches the expected output. For example, a developer might verify that a sort function called on the list [2, 10, 5, 4] would return the output [2, 4, 5, 10]. However, exhaustively covering a program with tests like this is challenging: bugs frequently remain in an edge case the developer did not test. After all, if a developer does not think to test an edge case, it is also likely the developer did not consider that case in the implementation!</p><p class="PA4F1q_reading-column post-text">In contrast, <em>property-based testing</em>&nbsp;is a software testing paradigm that aims to test whether a general property of the code holds for all (or most) inputs. A developer specifies a property or invariant about the program—for example, that JSON deserialization is the inverse of serialization—as well as a description of the kinds of inputs the property accepts (e.g., any JSON serializable objects). The property-based testing framework then automatically searches for a counterexample of this property by generating valid inputs as test cases using techniques similar to fuzzing. Since the developer specifies the general input domain, and not individual test cases, property-based testing frees developers from thinking of every edge case and allows them to operate at a higher level of abstraction.</p><p class="PA4F1q_reading-column post-text">In our paper that we presented at the 2025 NeurIPS <a id="base-ui-_R_7k7drpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://dl4c.github.io/"><em>Deep Learning for Code</em></a>&nbsp;Workshop that was the result of a <a id="base-ui-_R_7o7drpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://www.matsprogram.org/">MATS</a> project, we developed an AI agent that autonomously writes property-based tests for existing code. We directed the agent to discover properties by reading type annotations, docstrings, function names, and comments. The agent then wrote corresponding property-based tests using Hypothesis.</p><p class="PA4F1q_reading-column post-text">For this work, we focused on the problem of identifying bugs in general, and not just security vulnerabilities. Many classes of logic bugs that cause security vulnerabilities are amenable to property-based testing. For example, in a recent <a id="base-ui-_R_7k8drpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://red.anthropic.com/2025/smart-contracts/">blog post</a>&nbsp;we focused on identifying bugs in <em>smart contracts</em>; almost all of those vulnerabilities are the result of logic bugs. In the future we imagine that it may be possible to apply techniques such as the one we describe here to proactively identify bugs&nbsp;before deployment.</p><p class="PA4F1q_reading-column post-text">We used our agent and discovered hundreds of potential bugs in popular open-source Python repositories&nbsp;like NumPy, SciPy, and Pandas. In order to responsibly disclose these bugs and to ensure we don’t unnecessarily burden maintainers, we carefully reviewed each bug.</p><p class="PA4F1q_reading-column post-text">The review process we used is more laborious than we would otherwise implement for our own code reviews, but we strongly preferred to reduce the number of false positives. Our process was as follows: first, we only selected the highest priority bugs for review. We sent these potential bugs to be reviewed by three expert humans (for an average of one hour of review per bug). We then discarded any bug where any of the three manual reviewers were uncertain of its validity. Finally, we (the authors of this blog) manually reviewed each of the candidate bugs. Only if we were also confident in its correctness did we then manually file an issue with the maintainer of the repository.&nbsp;We have already filed several of these bug reports, and are in the process of filing many more.</p><p class="PA4F1q_reading-column post-text">We’ve made available all of our data, including bugs that have not yet been validated, and, for completeness, even bugs that we determined to be invalid, so that maintainers can look at them at this <a id="base-ui-_R_3sbdrpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://mmaaz-git.github.io/agentic-pbt-site/">site</a>.&nbsp;Over the coming weeks we intend to file many of these remaining bugs (after additional validation), as well as expand our project to additional PyPI projects.</p><div class="PA4F1q_media-column" data-type="codeBlock"><div class="PbWBnq_container"><div class="PbWBnq_code-container"><div class="PbWBnq_header"><div An example-based unit test verifies specific manually-specified inputs. A property-based test, in contrast, specifies a general property (e.g., the definition of a sorted list) and relies on the framework to automatically construct inputs that might fail this property.</div></figcaption></div></div></div><h2 class="tOQyXa_headline-4 PA4F1q_reading-column post-heading" data-component="Headline" id="our-property-based-testing-agent">Our Property-Based Testing Agent</h2><p class="PA4F1q_reading-column post-text">Our property-based testing agent is built as a custom Claude Code command. The agent takes a single argument, pointing it towards a particular target, either a single Python file (e.g., normalizers.py), a module (e.g., numpy, scipy.signal), or a function (e.g., requests.get, json.loads). The agent then follows this process to identify potential bugs:</p><ol class="PA4F1q_reading-column text-body-1-serif post-text"><li>Read and understand the target, by reading code, pulling relevant documentation, and exploring how it relates to the rest of the codebase.</li><li>Propose properties grounded in these findings.</li><li>Write corresponding property-based tests in Hypothesis.</li><li>Run the tests and reflect: if it failed, has the test truly discovered a bug, or does the test need to be adjusted? If it succeeded, is the test testing anything worthwhile, or is it simply trivial?</li><li>If the agent is confident it has found a real bug, it writes out a formatted bug report.</li></ol><div class="PA4F1q_media-column" data-type="image" data-width="inline-width"><figure class="Duq99q_e-imageWithCaption"><img alt="" loading="lazy" width="1999" height="1126" decoding="async" data-nimg="1" style="color:transparent" src="https://origin-ten-jet.vercel.app/sites/anthropic/pages-assets/fddde8bc9bdc5358e313.webp"><figcaption style="--figure-label:&quot;Figure 2&quot;" class="RMuY0W_root -LJkNq_container -LJkNq_container--default" data-component="RichTextWrapper"><div class="tOQyXa_caption-1 -LJkNq_text" data-component="Caption">The workflow of the agent.</div></figcaption></figure></div><p class="PA4F1q_reading-column post-text">To help the agent perform long-range multi-step reasoning, we direct it to use a to-do list to track its progress.</p><p class="PA4F1q_reading-column post-text">A priority in designing the agent was reducing the number of false alarms—from our personal experience, useful developer tooling minimizes the amount of incorrect reports presented to the developer. The self-reflection loop helps reduce the number of false alarms, as does grounding any properties in explicit usage and documentation of the target. For example, in one of the agent runs, the agent wrote a property that first passed. However, after self-reflection, the agent realized that it had wrapped the whole test in a try-catch block. After removing that, the test failed, and the agent found a bug. We also observed a notable improvement in self-reflection with Opus 4.1 and Sonnet 4.5, compared to Sonnet 4.</p><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="example-run">Example run</h3><p class="PA4F1q_reading-column post-text">To demonstrate how the agent works through testing a target, we show a paraphrased transcript where Claude identifies a bug in the implementation of numpy.random.wald. The agent begins with investigating the function, its signature, its docstring, and even existing tests:</p><div class="PA4F1q_media-column" data-type="artifactEmbed" data-width="full-width"><div class="jMbSuG_iframe-wrapper" style="padding-bottom:100%"><iframe src="https://origin-ten-jet.vercel.app/sites/anthropic/pages-assets/3fe291b775f3a7afb3c2.html" class="jMbSuG_iframe" title="Embedded artifact" loading="lazy" sandbox="allow-scripts"></iframe></div></div><p class="PA4F1q_reading-column post-text">Note that the fix is not correct; when we fixed this bug, we traced the source of the error to a numerically unstable calculation; see our merged fix <a id="base-ui-_R_3smdrpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://github.com/numpy/numpy/pull/29609">here</a>.</p><h2 class="tOQyXa_headline-4 PA4F1q_reading-column post-heading" data-component="Headline" id="searching-for-bugs-in-real-pypi-packages">Searching for bugs in real PyPI packages</h2><p class="PA4F1q_reading-column post-text">In order to test our agent’s abilities in the real world, we curated a diverse set of over 100 popular Python packages. These libraries span a variety of domains, from numerical computing to parsing to databases. We called our agent on each of these packages, and collected all generated bug reports.</p><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="evaluating-the-agent">Evaluating the agent</h3><p class="PA4F1q_reading-column post-text">For the first phase of our evaluation, which is covered in our paper, we ran the agent with Claude Opus 4.1 on each package and collected all generated bug reports. To evaluate these bug reports, we settled on two criteria: first, "is this a valid bug?", and second, "is this both a valid bug, and something we would reasonably report to the library maintainers?" The second criteria is stricter than the first, as, e.g., a bug might be valid, but too minor to file a report for.</p><p class="PA4F1q_reading-column post-text">Of the 984 bug reports, we manually selected 50 to review. We found that 56% of those reports were valid bugs, and 32% were valid bugs that we would also report.</p><p class="PA4F1q_reading-column post-text">Based on this manual review, we developed a rubric that ranks bugs out of 15, with the intent of surfacing bugs that are most likely to be valid and worth fixing to the developer. We used Opus 4.1 to score all bug reports according to this rubric. We found that this ranking step was considerably effective: of the top-scoring bug reports, 86% were valid, and 81% were both valid and reportable.</p><p class="PA4F1q_reading-column post-text">In the second phase of our evaluation, we ran the agent with Sonnet 4.5 on a subset of 10 important packages, running it on each package multiple times. We also developed an evaluation agent that used Sonnet 4.5 to read the code and the bug report to check the correctness and severity of the bug, which was more sophisticated than the rubric from the first phase. Lastly, we paid 3 expert human reviewers to evaluate high-severity bugs for correctness.</p><p class="PA4F1q_reading-column post-text">To read all the bug reports our agent found, see <a id="base-ui-_R_3sudrpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://mmaaz-git.github.io/agentic-pbt-site/">https://mmaaz-git.github.io/agentic-pbt-site/</a>.</p><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="maintainer-validation">Maintainer validation</h3><p class="PA4F1q_reading-column post-text">Evaluating the effectiveness of any tool which discovers bugs in code is difficult. While we try our best to validate the correctness of bug reports, the package maintainers serve as the ultimate arbiter of truth. To validate that our agent finds bugs that maintainers consider valid and worth fixing, we selected five particularly interesting bugs and manually reported these to their respective GitHubs, along with a proposed patch. Over the coming weeks, we intend to continue reporting additional bugs as we verify.</p><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="numpy">numpy</h3><p class="PA4F1q_reading-column post-text">numpy.random.wald sometimes returns negative numbers, which is a bug because samples from the Wald distribution should only return positive numbers. This is the bug demonstrated in our example run above. Claude knew this as a property of the Wald distribution and wrote a straightforward PBT to see if all samples generated are positive. We traced the error to a catastrophic cancellation occurring in the code, and developed a more numerically stable formulation when we submitted the pull request.&nbsp;As shown by the NumPy maintainers in the pull request, our reformulation has nearly ten orders of magnitude lower relative error than the previous algorithm.</p><p class="PA4F1q_reading-column post-text"><em>Patch merged: <a id="base-ui-_R_7r3drpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://github.com/numpy/numpy/pull/29609">https://github.com/numpy/numpy/pull/29609</a></em></p><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="aws-lambda-powertools-">aws-lambda-powertools </h3><p class="PA4F1q_reading-column post-text">slice_dictionary() returns the first chunk repeatedly, due to not incrementing the iterator. This was caught by our agent by identifying that slicing and then reconstructing the dictionary should return the original dictionary.</p><p class="PA4F1q_reading-column post-text"><em>Patch merged: <a id="base-ui-_R_fj6drpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://github.com/aws-powertools/powertools-lambda-python/pull/7246">https://github.com/aws-powertools/powertools-lambda-python/pull/7246</a></em> </p><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="cloudformation-cli-java-plugin">cloudformation-cli-java-plugin</h3><p class="PA4F1q_reading-column post-text">item_hash() produces the same value of hash(None) for all lists, due to use of the in-place .sort() method, which returns None. The agent caught this by testing that hashes of different inputs should be different.</p><p class="PA4F1q_reading-column post-text"><em>Patch submitted: <a id="base-ui-_R_fj9drpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://github.com/aws-cloudformation/cloudformation-cli/pull/1106">https://github.com/aws-cloudformation/cloudformation-cli/pull/1106</a></em>    </p><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="tokenizers">tokenizers</h3><p class="PA4F1q_reading-column post-text">EncodingVisualizer.calculate_label_colors()&nbsp;is missing a closing parenthesis, returning invalid HSL CSS. Our agent identified this by testing that the output should match the regex for a HSL color code.</p><p class="PA4F1q_reading-column post-text">Patch merged: <a id="base-ui-_R_3tcdrpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://github.com/huggingface/tokenizers/pull/1853">https://github.com/huggingface/tokenizers/pull/1853</a>  </p><h3 class="tOQyXa_headline-5 PA4F1q_reading-column post-section" data-component="Headline" id="python-dateutil">python-dateutil</h3><p class="PA4F1q_reading-column post-text">easter()&nbsp;returns a non-Sunday date for some years when using the Julian calendar. Maintainers identified the behavior as intended due to differing calendar systems, and acknowledged the semantics as subtle.</p><p class="PA4F1q_reading-column post-text"><em>Issue invalid: <a id="base-ui-_R_7rfdrpbsnpfkq6btb_" data-base-ui-tooltip-trigger="" href="https://github.com/dateutil/dateutil/issues/1437">https://github.com/dateutil/dateutil/issues/1437</a></em></p><p class="PA4F1q_reading-column post-text">The report to python-dateutil&nbsp;shows an important limitation of the agent: deriving properties from code with subtle or complex semantics remains difficult. If the code makes an implicit assumption, only the library maintainers can decide what the correct property to test is.</p><h2 class="tOQyXa_headline-4 PA4F1q_reading-column post-heading" data-component="Headline" id="conclusion">Conclusion</h2><p class="PA4F1q_reading-column post-text">As language models continue to improve, we think agentic property-based testing could become an increasingly valuable complement to human-written testing. The high-level semantic guarantees of property-based testing makes them a natural fit to pair with during development. We find that LLMs are particularly good at identifying properties that <em>should</em>&nbsp;be true about a given block of code from context (the name of the function, the docstring, how it is called by other functions, etc). This allows LLMs to write high quality property-based tests effectively.</p><p class="PA4F1q_reading-column post-text">Going forward, we believe that applying LLM to testing and bugfinding is an important research direction. Especially as LLMs improve at the process of exploiting vulnerabilities, it is necessary to stay ahead of attackers using LLMs for exploitation.</p><p class="PA4F1q_reading-column post-text">While we do not focus on the automatic generation of patches in this work, this is a clear direction for future work. If it is possible to (nearly) completely specify the correctness properties of a block of code, then correcting the bug becomes significantly easier, and we believe that in the near future LLMs will be able to effectively propose high-quality patches that are worth the consideration of maintainers.</p></div></div></article></div><!--$--><!--/$-->13:I[27155,["/_next/static/chunks/3fntmmi971322.js","/_next/static/chunks/2d9czp0wlvhe3.js","/_next/static/chunks/1h1qso4v7m_ly.js"],"PageRuntime"]
